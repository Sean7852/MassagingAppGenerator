# MassagingAppGenerator

A spec-driven **code generator** for messaging clients, built as a Claude Code harness.

You write the behavior once in a spec. The harness then generates two clients in different
languages (Python and TypeScript) that talk to each other through a small local server.
The generator is the deliverable. The messaging app is the example used to evaluate it.

> **Core promise:** delete `clients/`, run the generator, and you get working clients back
> that pass the same conformance tests.

> **Status:** spec version 4. v2 brought the offline outbox saved on disk, `/offline` and
> `/online`, and friendly and `--machine` output. v3 added **read receipts** as the first
> extension module ([spec/extensions/](spec/extensions/)), with no change to the harness. v4
> makes `/login` happen on every launch, with each user's queued messages kept in a folder
> named after them. Both clients are generated from it and pass all 13 conformance scenarios in
> all four pairings (52/52), including the assignment's Alice/Bob offline scenario.
> Design rationale, decisions and the schedule are in [DESIGN.md](DESIGN.md).

## Regeneration boundary

**Everything under `clients/` is generated and is never edited by hand.** Each client folder contains:

- `GENERATED.md`: marks the folder as generated and names the spec it came from.
- A `GENERATED — do not edit` header at the top of every source file.
- `.manifest.json`: spec hash, generation date, and test result.
- `ASSUMPTIONS.md`: platform-internal choices the agent made where the spec left room.

If generated code is wrong, the fix goes into `spec/` or the harness, followed by a regeneration.
Everything outside `clients/` is hand-crafted (human-led, AI-assisted).

Commit prefixes show who did what: `spec:`, `harness:`, `server:`, `test:`, `docs:` are
hand-crafted work, and `gen:` is generator output.

## Quick start

### Prerequisites
- Python 3.13+
- Node.js 24+ and npm
- [Claude Code](https://claude.com/claude-code) (only needed to regenerate clients)

```bash
pip install -r requirements.txt
```

### 1. Start the server
```bash
python server/server.py --port 8765
```

### 2. Run the clients
In two separate terminals:
```bash
python clients/python/main.py
```
```bash
cd clients/typescript && npm install && npm run build && node dist/main.js
```
Then type `/login alice` in one and `/login bob` in the other. Both connect to
`ws://127.0.0.1:8765` unless you pass `--server <url>`. Each user's unsent messages are saved
in `.msgdata/<name>/`, which Git ignores, so running the clients leaves the repo clean.

### 3. Using the client

| Command | Effect |
|---|---|
| `/login <name>` | Log in, on every launch (the name is not remembered). Your queued messages come back and are sent. If the server is down, you are logged in offline and can still queue messages. |
| `/send <user> <text>` | Queue a message and send it as soon as you are online. |
| `/offline` | Drop the connection (simulates losing the network). Messages you send are queued. |
| `/online` | Reconnect and send everything queued, oldest first. |
| `/quit` | Exit. Queued messages are kept on disk for next time. |

**How a `/send` line is read.** `/send`, one space, the recipient's name (up to the next space),
one space, and then the message: **everything after that space, to the end of the line, exactly
as typed**. Spaces, emoji, tabs and any other characters are part of the message; nothing is
trimmed. So `/send bob  hi` sends ` hi` with a leading space. Names are lowercase letters,
digits and `_` (the server checks this). A message may be at most 8192 bytes.

**Going online holds everything up.** While the client connects and logs in (after `/login`
or `/online`), it handles no other command. Anything you type meanwhile waits and
runs afterwards, in order. If the server is unreachable this takes up to 5 seconds and ends with
an error; your queued messages stay queued.

**What you see.** By default the client prints friendly lines:
```
Logged in as alice
[queued] to bob: Hi Bob
[sent]   to bob (#1)
[bob] What is it?
You are offline. Messages will be queued.
```
With `--machine` it prints exact keyword lines instead (`QUEUED id=… to=bob`, `SENT id=… seq=1
to=bob`, …), which the tests use. Every line, error and rule is defined in
[spec/core/30-cli.md](spec/core/30-cli.md) and [spec/core/20-client.md](spec/core/20-client.md).

**Read receipts.** When the other person's client shows your message, you see
`[read]   by bob (#3)` (or `READ id=… seq=3 by=bob` with `--machine`). If you are offline, the
receipt waits on the server and appears when you are back.

**Losing the connection.** If the server goes away, the client prints that it was disconnected
and goes offline. It does not reconnect by itself; type `/online`. Nothing you sent is lost.

## Regenerate the clients

**Interactive, in Claude Code** (from the repo root):
```
/generate all
```
Use `/generate python` or `/generate typescript` for a single client.

**Headless** (no interactive session needed):
```bash
python harness/regenerate.py --platform all
```

Both are the same pipeline (`/generate` just runs the script). Scripts run it; AI agents are
used only to write and to fix a client, and scripts plus real tests judge the result:

```
regenerate.py
 ├─1─► spec_gate.py         stop if spec/OPEN_QUESTIONS.md has a blocking question
 │   for each platform:
 ├─2─► clean.py             delete clients/<platform>/
 ├─3─► client-generator     AI agent: reads spec/ + scenarios, writes clients/<platform>/ only
 ├─4─► verify.py            headers, setup, build, unit tests, then conformance/run.py
 │                          (starts server/server.py and real client processes)
 ├─5─► client-fixer         AI agent, only if step 4 failed: reads the report, fixes, back to 4
 │                          (at most 3 rounds)
 ├─6─► manifest.py          .manifest.json + GENERATED.md: which spec this came from
 └─7─► verify.py (cross)    py↔ts and ts↔py through the same server
```

- Each agent may only write its own `clients/<platform>/`; the run fails if anything else
  changed. **Do not edit files during a run**: the check cannot tell your edits from the agent's.
- If an agent finds a question the spec does not answer, it writes `BLOCKED.md` and the run
  stops instead of guessing.
- Agent transcripts are kept in `harness/.runs/` (not committed).
- Each client takes about 5 minutes. The agents run through your Claude Code login: on a Claude
  subscription this uses your plan's usage limits; with an API key it is billed per token. The
  dollar figures the script prints are Claude Code's API-price estimates, not charges.
  `--model claude-sonnet-5-5` uses less.

To check that regeneration works from scratch:
```bash
git rm -r -q clients && python harness/regenerate.py --platform all
```

## Run the tests

Server protocol tests (raw WebSocket frames, no clients needed):
```bash
python server/test_server.py
```

Build, unit-test and conformance-test the generated clients (all pairings), without regenerating:
```bash
python harness/verify.py all
```

Conformance tests only (clients must already be built):
```bash
python conformance/run.py
```

This runs every scenario in `conformance/scenarios/` against all four client pairings
(py↔py, ts↔ts, py↔ts, ts↔py), including the assignment's Alice/Bob offline scenario
(`08_alice_bob_offline.yaml`), restarts and crashes, and a server outage.
Use `--scenario <name>` or `--pair py-ts` to narrow it down.

## Changing the spec

1. Edit or add a module under `spec/` (for a new feature, add a file under `spec/extensions/`).
2. Add or update scenarios in `conformance/scenarios/`.
3. Run `/review-spec` in Claude Code. The `spec-reviewer` agent looks for places where two
   clients could behave differently, and lists them in `spec/OPEN_QUESTIONS.md`: blocking if
   the difference would be visible, non-blocking otherwise. It does not change the spec.
4. Run `/clarify-spec`. Claude walks you through the open questions; you decide, and each
   answer is written into the spec and recorded in `spec/decisions/`.
5. Run `/generate all`. It refuses to start while `spec/OPEN_QUESTIONS.md` has an unchecked
   blocking question (`python harness/spec_gate.py` shows the same check).

Steps 3 and 4 are interactive and happen before generation, so generation itself never has to
ask anything and can run unattended. The review is not part of `/generate`: an AI review on
every run would make generation less repeatable, so the gate only reads the questions file.

The harness is not tied to one version of the spec, so new modules should regenerate without
changing the harness.
